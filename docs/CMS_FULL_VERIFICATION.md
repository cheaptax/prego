# 전체 CMS 및 관리자 콘솔 최종 검증 보고서

검증일: 2026-07-21  
범위: 로컬 코드 기본값, 메모리 Firestore, Firebase Firestore·Storage Emulator, 격리된 Playwright 개발 서버  
제외: 운영 배포, 운영 데이터 읽기·쓰기·마이그레이션, 운영 계정 로그인

## 1. 전체 전환 라우트

중앙 CMS 등록부에 등록된 사용자 화면은 17개다.

- `/` 메인 화면
- `/events/audit-quote` FY27 회계감사 견적
- `/login` 로그인·계정 찾기
- `/signup` 회원가입
- `/inquiries` 문의게시판
- `/consult` 상담 신청
- `/support` 고객지원
- `/faq` 자주 묻는 질문
- `/mypage` 마이페이지
- `/mypage/requests/[requestId]` 상담 요청 상세
- `/pending-approval` 가입 승인 대기
- `/terms` 이용약관
- `/privacy` 개인정보처리방침
- `/partner` 파트너 안내
- `/admin` 관리자 콘텐츠 콘솔
- `/admin/operations` 관리자 운영 화면
- `/_not-found` 찾을 수 없는 화면

관리자 전용 편집기 `/admin/pages/[pageKey]`와 `/admin/globals/[documentKey]`는 사용자 콘텐츠 화면이 아니므로 예외 문서에 사유, 담당자, 재검토일과 함께 등록했다. 공통 로고·헤더·내비게이션·푸터·고객지원 버튼은 페이지별 복사본 없이 공통 영역으로 관리한다. 미전환 사용자 화면은 발견되지 않았다.

## 2. 관리자 메뉴와 주요 사용법

1. 관리자 권한이 있는 계정으로 로그인하고 `콘텐츠 관리`에서 업무용 화면 이름을 선택한다.
2. 문구, 카드, 이미지, 버튼·링크, 디자인, SEO 탭에서 내용을 편집한다.
3. 자동저장 상태가 `저장됨`인지 확인하고 PC·태블릿·모바일 미리보기를 확인한다.
4. `게시 전 확인`에서 게시 내용과 초안의 문구·링크·순서·이미지·디자인 차이를 확인한다.
5. 필수 항목, 제목 구조, 대체 텍스트, 대비 경고를 해결한 뒤 게시한다.
6. `수정·게시 이력`에서 이전 버전을 초안으로 복원하고, 미리보기 후 다시 게시하면 롤백이 완료된다.

동시에 편집해 저장 버전이 어긋난 경우 덮어쓰지 않고 최신 내용을 다시 불러오도록 안내한다. 저장 중 추가 변경은 다음 자동저장으로 이어지며, 저장하지 않은 변경이 남은 상태에서 창을 닫으면 경고한다. 이미지와 메뉴의 `삭제`는 영구 삭제가 아니라 고객 화면에서 숨기고 초안에 보관하는 방식이며 편집기에서 복원할 수 있다.

## 3. 편집 가능한 콘텐츠와 디자인

- 화면 제목, 배지, 본문, 강조문구, 카드, 단계, FAQ, 빈 화면·권한·성공·실패·검증·로딩 안내
- 버튼 표시명, 안전한 내부·외부 링크, 입력 라벨·placeholder·도움말
- 로고와 콘텐츠 이미지, 대체 텍스트, 캡션, 비율
- 반복 카드 추가·순서 변경·숨김·복원
- 허용 범위 내 색상 토큰, 글꼴, 데스크톱·태블릿·모바일 글자 크기, 간격, 정렬, 카드·버튼 모양
- SEO 제목·설명·공유 이미지
- 법적 문구와 동의 표시 문구. 단, 필수 문구는 숨기거나 영구 삭제할 수 없고 수정 경고와 이력을 남긴다.

비개발자 편집 시나리오인 메인 제목 변경, 모바일 글자 크기 변경, 카드 순서 변경, FAQ 추가, 이미지 교체, 초안 비공개 확인, 게시, 이전 버전 복원·재게시까지 메모리 Firestore 통합 테스트로 재현했다.

## 4. 보호된 기능 로직

- Firebase 인증, 관리자 custom claim, 회원 승인·농협 소속 확인, 이메일·휴대폰 인증
- 문의 공개 범위, 저장·조회·첨부 권한, 상담 완료 순서
- input `name`, API 경로, Firestore 컬렉션·필드명, Storage 경로, 요청 payload
- 감사견적 honeypot, 본문 크기, origin, rate limit, idempotency, HMAC 이메일 해시, 필수 개인정보 동의와 상태 전이
- 관리자 탭·필터의 내부 값, 운영 권한, 포인트 원장과 알림 요청 구조

CMS 값은 위 항목의 입력으로 전달되지 않는다. 감사견적은 CMS 전후 동일한 endpoint와 payload를 생성하는 경계 테스트를 통과했다.

## 5. 보안 검증 결과

- Firestore 공개 읽기는 게시 문서만 허용하고, 초안·수정 이력·감사 로그·이미지 메타데이터는 guest와 member에게 차단했다.
- 관리자도 브라우저에서 CMS 문서를 직접 쓰지 못하며, custom claim을 확인하는 서버 API만 저장·게시·복원한다.
- Storage는 게시 이미지 공개 읽기, 관리자 초안 업로드만 허용한다. MIME 허용 목록, 10MB 제한, 안전한 경로를 검사한다.
- CMS 업로드 완료 API는 메타데이터뿐 아니라 JPEG·PNG·GIF·WebP·PDF 파일 시그니처를 검사하고 불일치 파일을 삭제한다.
- 명함은 소유자 최초 생성만 허용하고 덮어쓰기·수정·삭제와 위험 MIME을 차단한다.
- 악성 마크업, 실행 가능한 URL, 임의 스타일 필드, 중복 ID, 필수 법적 영역 제거는 런타임 스키마 또는 게시 전 검사에서 거부한다.
- Firebase Emulator 실제 규칙 테스트 85개가 통과했다. 운영 데이터에는 접근하지 않았다.

## 6. 테스트 결과

- `npm run typecheck`: 통과
- `npm run lint`: 통과, 편집 파일 IDE 진단 0건
- `npm test`: 111개 통과, 실패 0
- `npm run test:integration`: 6개 통과, 실패 0
- `npm run test:cms:rules`: 85개 통과, 실패 0
- `npm run test:e2e`: 17개 라우트 × 3개 화면 크기 = 51개 시나리오 통과
- `npm run cms:audit`: 사용자 route 19개 = CMS 등록 17개 + 문서화된 편집기 예외 2개
- `npm run build`: Next.js 16.2.4 production build 통과

E2E 결과는 브라우저 콘솔 오류 0건, 실패 0건, 최대 CLS 0.0532였다. 모든 검사는 격리된 로컬 환경에서 실행했고 신청·배포·마이그레이션 같은 운영 부작용은 발생시키지 않았다.

## 7. 성능 확인 결과

- 공개 메인 화면은 게시 페이지 1건을 한 번 읽고, 공통 영역 4건을 `getAll` 한 번으로 묶어 총 5개 문서를 읽는 계약을 통합 테스트로 고정했다.
- 서버 `cache`로 같은 렌더 요청의 중복 CMS 읽기를 줄였고, 삭제한 이미지 ID는 URL 조회와 게시 복사에서 제외했다.
- 51개 브라우저 시나리오에서 최대 CLS는 0.0532로 기준 0.1 이하였다.
- E2E 최대 DOMContentLoaded는 3,068ms였다. 이는 격리된 Next.js 개발 서버의 최초 컴파일을 포함하므로 운영 성능 수치나 Core Web Vitals로 해석하면 안 된다.
- 모바일 14px 가로 넘침을 수정했고, Pretendard를 로컬 제공·preload하여 폰트 교체에 따른 레이아웃 이동을 줄였다.

## 8. 운영 반영 전에 사람이 해야 할 작업

- 스테이징 Firebase 프로젝트에서 실제 guest·승인 대기 member·승인 member·admin 테스트 계정으로 로그인 전후 화면과 권한을 브라우저에서 확인한다.
- 실제 관리자 화면에서 대표 이미지 1개를 업로드하고, 미리보기·게시·삭제 보관·복원·재게시 후 Storage 객체와 공개 URL을 확인한다.
- 법무 담당자가 개인정보 동의, 이용약관, 면책문구의 최종 문구와 버전을 승인한다.
- 콘텐츠 담당자가 PC·태블릿·모바일에서 기존 운영 화면과 스크린샷을 육안 비교한다.
- 스테이징에서 실제 Firebase read 수, 캐시 적중, 이미지 용량, LCP·INP·CLS를 관측한다.
- 배포 전 환경 변수, Firebase Admin 자격증명, Auth custom claim 부여 절차, 인덱스와 Rules 대상 프로젝트를 이중 확인한다.
- 최초 게시 콘텐츠와 공통 영역의 담당자 승인 및 복구 기준 버전을 확정한다.

## 9. 남아 있는 제한사항

- 이번 자동 브라우저 E2E는 운영 접근을 막기 위해 코드 기본값과 읽기 전용 guest 경로를 사용했다. member와 admin은 권한·renderer·API·Rules·repository 테스트로 검증했지만 실제 로그인 세션을 포함한 브라우저 E2E는 스테이징 계정으로 한 번 더 확인해야 한다.
- 이미지 업로드는 시그니처 검사, Storage Rules, 게시 복사, 삭제 보관·복원을 각각 자동 검증했다. 실제 브라우저 파일 선택부터 공개 CDN 표시까지의 단일 종단 시나리오는 스테이징 확인 대상이다.
- 접근성 자동 검사는 이름 없는 버튼·링크, 입력 라벨, 키보드 dialog 동작, 가로 넘침을 검사한다. 스크린리더 읽기 순서와 저시력 사용자 평가는 수동 검사가 필요하다.
- 픽셀 단위 시각 회귀 기준 이미지는 없다. 모바일 넘침과 폰트 로딩을 수정했으므로 과거 화면과 완전히 동일하다고 주장할 수 없다.
- 개발 테스트 로그에는 Node의 `punycode` deprecation과 TypeScript 파일의 module-type 경고가 남는다. 기능 실패는 아니지만 향후 도구 체인 정리 대상이다.
- Firestore 5-read 수치는 저장소 계약 테스트 결과이며 실제 운영 청구·지역 네트워크·CDN 캐시 성능을 대신하지 않는다.

## 10. 배포 및 마이그레이션 권장 순서

1. 현재 변경을 별도 검토 브랜치에서 보안·콘텐츠·법무 담당자가 승인한다.
2. 스테이징 프로젝트에 Firestore·Storage Rules와 필요한 인덱스를 먼저 적용한다.
3. 애플리케이션을 스테이징에 배포하고 8번의 실제 계정·이미지·접근성·성능 확인을 완료한다.
4. 코드 기본값과 동일한 최초 CMS 문서를 dry-run으로 비교하고 백업한다.
5. 운영 Rules를 적용한 뒤 애플리케이션을 배포한다. 기존 공개 화면은 CMS 문서가 없어도 코드 기본값으로 유지된다.
6. 공통 영역을 먼저 초안 저장·미리보기·게시하고, 그다음 사용자 화면을 저위험 화면부터 순차 게시한다.
7. 법적 화면과 감사견적 화면은 법무 승인 직후 별도 게시한다.
8. 각 게시 직후 공개 화면, 인증 흐름, 폼 payload, Firestore·Storage 오류율과 read 수를 확인한다.
9. 이상이 있으면 해당 CMS 이력에서 이전 버전을 초안으로 복원·게시하고, 애플리케이션 문제면 직전 배포로 롤백한다.

운영 배포와 운영 데이터 마이그레이션은 이번 작업에서 수행하지 않았다.
